# Contributing to Parlora

Thanks for your interest in Parlora. This guide explains how work is planned,
how to set up the project, and what a pull request needs before it can be
merged.

Parlora is **source-available under the PolyForm Noncommercial License
1.0.0**, not open source. Contributions are accepted under a
[Contributor Licence Agreement](CLA.md) (see [below](#contributor-licence-agreement)).

## Before you start

- **Open or pick an issue first.** Every change is tracked by an issue, and
  the issue is the specification: it carries the context and the acceptance
  criteria. Use the issue forms (feature, bug, chore, spike).
- **Security problems** go through private vulnerability reporting, never a
  public issue: see [SECURITY.md](SECURITY.md).
- **Questions** belong in [SUPPORT.md](SUPPORT.md)'s channels, not in issues.
- Comment on the issue before starting larger work, so effort is not
  duplicated.

## Development setup

Requirements: git, [uv](https://docs.astral.sh/uv/), Node.js 24 LTS with
corepack (for pnpm), and Docker Desktop (with WSL2 and NVIDIA GPU support on
Windows) for the local stack and integration tests.

```sh
uv run just setup   # install Python and JavaScript dependencies and the git hooks
uv run just check   # run every gate CI runs: lint, types, tests, security
uv run just --list  # all recipes
```

Prefer not to install anything? Open the repository in its
[Dev Container](.devcontainer/), which ships the whole toolchain.

## How we work

1. **Branch** from `main` as `<type>/<issue>-<slug>`, for example
   `feat/42-cefr-level-picker`.
2. **Test first.** Domain logic is written test-first; every change includes
   its tests. Coverage gates: domain core ≥ 95 % (lines and branches), server
   and web ≥ 85 %.
3. **Commit** with [Conventional Commits](https://www.conventionalcommits.org/):
   `<type>(<scope>): <description>`, imperative and lowercase, with a body that
   explains _why_. Types: `feat`, `fix`, `perf`, `refactor`, `docs`, `test`,
   `build`, `ci`, `style`, `chore`, `revert`. Scopes: `core`, `server`, `web`,
   `infra`, `ci`, `docs`, `deps`, `repo`. The commit-msg hook checks this.
4. **Open a pull request** using the template. The title follows the same
   format (it becomes the commit on `main`, because pull requests are
   squash-merged) and the body links the issue with `Closes #N`.
5. **CI must be green**: the single required check is `ci-ok`.

Versions and the changelog are generated by release-please from the commit
history; never bump versions by hand.

## Privacy and security rules

- Never commit real voice recordings, transcripts or any personal data.
  Test audio must be synthetic and live under a `fixtures/synthetic/` folder.
- Never commit secrets, credentials, model weights or local absolute paths.
  The gitleaks hook and CI scan for secrets.
- New dependencies must have a licence compatible with the project: no GPL
  or AGPL code in the Parlora process. CI checks every dependency change.

## Contributor licence agreement

Before your first pull request can be merged you must accept the
[Contributor Licence Agreement](CLA.md). It lets the copyright holder keep
licensing Parlora, including under other terms, with your contribution in it;
you keep the copyright of your work. You accept it once, and it covers all
your future contributions.
